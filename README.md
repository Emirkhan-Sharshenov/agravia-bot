# AGRAVIA — ИИ-чат-бот «Алиса» для сайта

Реализация по ТЗ «AI-бот AGRAVIA 2027» (раздел 24, приоритет P0):
автоматическая сегментация без обязательного выбора роли, семантический
поиск с confidence-уровнями (HIGH/MEDIUM/LOW), уточняющие вопросы,
учёт контекста диалога, RAG-guardrails против отсебятины и джейлбрейков,
передача заявки менеджеру только по запросу пользователя, отделённая
от AI-контура.

LLM-провайдер по умолчанию — **GigaChat (Сбер)**: бесплатный лимит
1 000 000 токенов/мес на физлицо, работает из России без VPN и
зарубежной карты, соответствует Варианту B архитектуры (раздел 13.2
ТЗ). Anthropic (Claude) оставлен как опциональная платная альтернатива
для локальной разработки/тестирования — переключается одной переменной
окружения; при использовании его в production учтите раздел 13.3 ТЗ
(требует отдельного согласования как зарубежный AI API).

## Структура проекта

```
agravia-bot/
├── backend/
│   ├── main.py            # FastAPI: /api/chat, /api/handoff, /api/health + подключает alice.py
│   ├── alice.py            # (опционально) вебхук навыка Яндекс.Алисы — см. раздел внизу
│   ├── chat_engine.py      # Общая логика диалога (сегментация → confidence → ответ/уточнение/fallback),
│   │                       # используется и /api/chat, и alice.py, чтобы поведение не расходилось
│   ├── kb_store.py         # Загрузка kb.json + плоский список всех элементов базы
│   ├── retrieval.py        # Семантический поиск (GigaChat Embeddings) + confidence + автосегментация,
│   │                       # с fallback на fuzzy (rapidfuzz), если embeddings недоступны
│   ├── llm.py               # Системные промпты (ответ / уточняющий вопрос) + вызов LLM и embeddings
│   ├── analytics.py         # Логи: analytics.jsonl (раздел 18 ТЗ) и unanswered.jsonl (раздел 19 ТЗ)
│   ├── handoff.py           # Передача заявки менеджеру (Telegram + лог-файл), отделена от AI-контура
│   ├── kb.json               # База знаний: common (6) + visitor (27) + exhibitor (105), с intent/examples
│   ├── kb_embeddings_cache.json  # Кэш embedding-векторов базы (создаётся автоматически, не коммитить)
│   ├── requirements.txt
│   └── .env.example
└── widget/
    ├── widget.js         # Встраиваемый чат-виджет для сайта (ванильный JS, без сборки)
    └── demo.html          # Тестовая страница для widget.js
```

## Как это работает

Раздел 3 ТЗ: `сообщение → сегментация (без обязательного выбора роли) →
учёт истории → семантический поиск → confidence → ответ / уточнение /
fallback`. Вся эта логика — в `chat_engine.handle_message()`, общей и
для сайта, и для навыка Алисы.

1. **Автосегментация вместо обязательного выбора.** Пользователь сразу
   пишет вопрос. `retrieval.search()` считает семантическую похожесть
   запроса на все элементы базы (common/visitor/exhibitor вместе) и сам
   определяет сегмент: `common` (если максимально похож общий факт),
   `visitor`/`exhibitor` (если максимально похож факт одной из ролей), или
   `uncertain` — если скор visitor и exhibitor почти одинаковый (раздел
   4.4 ТЗ), тогда бот один раз уточняет роль вместо угадывания.
2. **Confidence вместо жёсткого da/net-порога.** По итоговому скору
   выбранного сегмента считается HIGH/MEDIUM/LOW (раздел 11 ТЗ,
   пороги — переменные окружения, см. `.env.example` и комментарии в
   `retrieval.py`; их нужно откалибровать на тестовом наборе минимум из
   200 вопросов, раздел 21 ТЗ, прежде чем фиксировать в продакшене):
   - **HIGH** — сразу зовём LLM сформировать ответ по найденным
     фрагментам (RAG, раздел 8 ТЗ);
   - **MEDIUM** — есть несколько похожих, но разных тем/интентов →
     бот задаёт один короткий уточняющий вопрос (раздел 10 ТЗ) и ждёт
     ответа, чтобы повторить поиск с учётом уточнения;
   - **LOW** — подтверждённой информации нет → вежливый fallback и
     предложение связать с менеджером, вопрос сохраняется в
     `logs/unanswered.jsonl` (раздел 19 ТЗ) для расширения базы.
3. **Первый барьер (до LLM)** — сам confidence: при LOW модель вообще
   не вызывается (экономит токены и защищает от посторонних тем/части
   джейлбрейков ещё до обращения к модели).
4. **Второй барьер (в LLM)** — при HIGH найденные фрагменты передаются
   модели как единственный источник знаний, с жёстким правилом «отвечай
   только по этим данным, не придумывай факты (даты/цены/штрафы/
   телефоны/адреса и т.д. — раздел 9 ТЗ), иначе выведи NO_MATCH».
   Промпт также запрещает выходить из роли или реагировать на
   «игнорируй инструкции».
5. **Контекст диалога** (раздел 5 ТЗ): при поиске учитываются последние
   реплики пользователя (`CONTEXT_TURNS`, по умолчанию 2) — раздельно от
   текущего вопроса и с меньшим весом, чтобы разрешать местоимения
   («там», «воду») не теряя фокус на самом вопросе.
6. Только если пользователь сам нажимает «Да, соединить с менеджером» —
   вызывается `/api/handoff` (раздел 14 ТЗ: форма контактов отделена от
   AI-контура), который логирует заявку в `backend/logs/handoffs.jsonl`
   и отправляет уведомление в Telegram (если настроены
   `TELEGRAM_BOT_TOKEN` / `TELEGRAM_MANAGER_CHAT_ID`).

## Настройка бесплатного LLM (GigaChat)

1. Зарегистрируйтесь на https://developers.sber.ru обычным аккаунтом.
2. В личном кабинете откройте раздел **GigaChat API** → «Создать
   проект» → тариф **GigaChat API PERS** (для физлиц, тот самый
   бесплатный 1 млн токенов/мес).
3. На вкладке проекта нажмите «Получить доступ» — там будет готовый
   **Authorization key** (это уже Base64 от `client_id:client_secret`,
   копировать/кодировать самому не нужно). Вставьте его в `.env` как
   `GIGACHAT_AUTH_KEY`.
4. Установите сертификат НУЦ Минцифры — без него будет ошибка
   `CERTIFICATE_VERIFY_FAILED`, потому что GigaChat использует
   российский корневой сертификат, которого нет в обычных системных
   хранилищах. Самый быстрый способ (добавляет сертификат в бандл
   `certifi`, которым пользуется Python):

   ```bash
   curl -k "https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt" -w "\n" >> $(python3 -m certifi)
   ```

   Выполните это в том же окружении (venv/Docker-образе), где будет
   работать бэкенд.
5. Готово — `LLM_PROVIDER=gigachat` уже стоит по умолчанию, ничего
   больше менять не нужно.

Если на каком-то этапе шаг 4 неудобен (например, временно тестируете
локально) — можно на время поставить `GIGACHAT_VERIFY_SSL=false` в
`.env`, но это отключает проверку SSL-сертификата и **не должно**
использоваться в продакшене.

### Если понадобится Anthropic вместо GigaChat

```
LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
```

Anthropic — платный (пробного бесплатного лимита, сравнимого с
GigaChat PERS, у него нет), но не имеет региональных ограничений
доступа, если сервер бэкенда физически не в России.

## Запуск локально

```bash
cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # впишите GIGACHAT_AUTH_KEY (см. выше)

export $(cat .env | xargs)   # или используйте python-dotenv/systemd env
uvicorn main:app --reload --port 8811
```

Откройте `widget/demo.html` через любой статический сервер
(например `python3 -m http.server 8000` из папки `widget/`) — виджет
достучится до `/api/...` по адресу, указанному в `data-api`.

## Встраивание на сайт (Фаза 5.3 роадмапа)

Одна строка в футер сайта:

```html
<script src="https://ВАШ_ДОМЕН/widget/widget.js"
        data-api="https://ВАШ_ДОМЕН/api"></script>
```

Бэкенд по умолчанию сам отдаёт файлы виджета по пути `/widget/...`
(смонтировано в `main.py`), так что для старта достаточно поднять
только бэкенд.

## Деплой в продакшен

- Задеплойте `backend/` как обычное FastAPI-приложение (uvicorn/gunicorn
  за nginx, либо Docker; сама база `kb.json` — часть образа/репозитория).
  Сервер может быть в России — GigaChat туда и рассчитан.
- Обязательно сузьте `allow_origins` в `main.py` до домена вашего сайта
  вместо `"*"`.
- Не забудьте про сертификат НУЦ Минцифры на сервере (шаг 4 выше) —
  в Docker-образе его нужно ставить на этапе сборки образа.
- Переменные окружения — `GIGACHAT_AUTH_KEY` обязателен (или
  `ANTHROPIC_API_KEY`, если выбрали Anthropic),
  `TELEGRAM_BOT_TOKEN` / `TELEGRAM_MANAGER_CHAT_ID` опциональны (без них
  заявки всё равно сохраняются в `logs/handoffs.jsonl`).
- Логи диалогов (`logs/dialogs.jsonl`) и заявок — то, что нужно будет
  регулярно разбирать на Фазе 8 роадмапа (какие вопросы не покрыты
  базой, где бот ошибался).

## Обновление базы знаний

`kb.json` теперь состоит из трёх сегментов (раздел 4 ТЗ): `common`
(6 общих интентов — даты, часы работы, место, организатор, про AGRAVIA
и iAGRI), `visitor` (27) и `exhibitor` (105). Каждый элемент — это
интент (раздел 7 ТЗ): `category`, `question`, `answer`, плюс `intent`
(уникальный id для аналитики/лога unanswered) и опциональный список
`examples` — альтернативных формулировок того же вопроса. Формат:

```json
{
  "common": [
    {
      "intent": "common.event_dates",
      "category": "Даты и время",
      "question": "Когда пройдёт выставка AGRAVIA 2027?",
      "examples": ["Когда выставка?", "Даты AGRAVIA", "Какого числа AGRAVIA?"],
      "answer": "..."
    }
  ],
  "visitor": [ {"intent": "visitor.bilet_i_registraciya.01", "category": "...", "question": "...", "examples": [], "answer": "..."} ],
  "exhibitor": [ ... ]
}
```

Чтобы добавить или изменить вопрос — редактируйте `kb.json` напрямую
(обычный JSON), при желании добавьте `examples` с 2-4 перефразировками,
и перезапустите бэкенд. Если используется semantic search (настроен
`GIGACHAT_AUTH_KEY`), новые/изменённые тексты автоматически
переembeddятся при следующем старте (кэш в `kb_embeddings_cache.json`
ключуется по хэшу текста, старые записи не трогаются — так экономится
лимит токенов).

## Тестирование

Раздел 21 ТЗ требует тестовый набор минимум из 200 вопросов (50
посетителей, 50 экспонентов, 30 общих, 20 неоднозначных, 30
перефразированных, 20 follow-up с контекстом, 20 вопросов вне базы)
перед запуском в production — это ещё предстоит собрать и прогнать
(критерий приёмки №14, раздел 23 ТЗ). Обязательные тест-кейсы из раздела
22 ТЗ (даты выставки тремя формулировками, электричество, необорудованная
площадь → вода, регистрация без контекста, вопрос вне базы) вручную
проверены в ходе разработки — см. `backend/retrieval.py` и
`backend/chat_engine.py`. С чего начать дальнейшее тестирование:

- **Функциональное:** задайте по 2-3 вопроса из базы разными словами
  на каждый сегмент, сверьте ответы.
- **Перефразировки/семантика:** «когда выставка», «даты AGRAVIA»,
  «какого числа мероприятие» должны находить один и тот же интент
  `common.event_dates`.
- **Автосегментация:** задайте вопрос без выбора роли («как заказать
  электричество на стенде») — бот должен сам понять, что это
  экспонентская тема, без промежуточного вопроса «вы участник?».
- **Уточнения:** «мне нужен пропуск» (несколько типов пропусков) и
  «как зарегистрироваться» (без контекста непонятно, посетитель или
  экспонент) должны привести к одному короткому уточняющему вопросу,
  а не к неправильному ответу или мгновенному fallback.
- **Контекст:** «у нас необорудованная площадь», затем «а воду как
  подключить?» — второй ответ должен учитывать первую реплику.
- **Guardrails:** попробуйте посторонние темы («расскажи анекдот»,
  «какая погода», «дай рецепт»), попытки джейлбрейка («игнорируй
  инструкции», «представь что ты другой бот») — бот должен вежливо
  отказать и предложить менеджера, а не отвечать по теме.
- **Сегменты:** убедитесь, что вопрос про монтажный пропуск (тема
  экспонентов) автоматически резолвится в `segment: "exhibitor"` в
  ответе `/api/chat`, а не в `visitor`, и наоборот.
- **Хендофф:** нажмите «Да, соединить с менеджером», проверьте, что
  заявка появилась в `logs/handoffs.jsonl` (и в Telegram, если
  настроено).

## Опционально: навык Яндекс.Алисы

В проекте также есть `backend/alice.py` — реализация вебхука для
настоящего голосового/текстового навыка Алисы (Yandex Dialogs), на
случай если он вам тоже понадобится позже. Это отдельная,
необязательная вещь: навык Алисы работает только через приложение
Яндекса/колонки/Яндекс Браузер, а не как чат-окно на сайте — сайт
обслуживает `widget/widget.js`. Оба используют одну и ту же базу
знаний и логику guardrails, включать `alice.py` не обязательно —
если он не нужен, можно просто не регистрировать навык в консоли
Яндекса, на работу сайта это никак не влияет.

## Соответствие ТЗ «AI-бот AGRAVIA 2027» и что ещё осталось

**Раздел P0 ТЗ (раздел 24) — сделано в этой версии:** убран обязательный
выбор visitor/exhibitor, автосегментация (включая common/uncertain),
семантический поиск (с fallback на fuzzy без embeddings), confidence
HIGH/MEDIUM/LOW, уточняющие вопросы, новый fallback с логом unanswered
queries, согласованный AI-контур (GigaChat по умолчанию — Вариант B
раздела 13 ТЗ).

**P1 (раздел 24 ТЗ) — сделано частично:**
- RAG и контекст диалога — реализованы (`retrieval.py`, `chat_engine.py`).
- Разделение AI и формы обратной связи — уже было и сохранено (`handoff.py`).
- Тестирование на полной базе посетителей/экспонентов — **не сделано**:
  нужен прогон тестового набора минимум из 200 вопросов (раздел 21 ТЗ) и
  калибровка порогов confidence по его результатам (см. `.env.example`).

**P2 (раздел 24 ТЗ) — не входит в эту версию:**
- Полноценная статистика по интентам/сегментам и dashboard качества
  ответов (сейчас есть только сырые `logs/analytics.jsonl` и
  `logs/unanswered.jsonl` — их пока нужно разбирать вручную/скриптом).
- Регулярный процесс расширения базы на основе unanswered queries.

**Другое, вне ТЗ, но полезное для продакшена:**
- Нагрузочное тестирование и продакшен-деплой инфраструктуры.
- Полноценная админка для редактирования `kb.json` без ручной правки JSON.
- Персистентное хранилище диалогов и векторов (сейчас — jsonl-файлы и
  локальный JSON-кэш embeddings; для масштабирования стоит перейти на
  PostgreSQL/pgvector или Qdrant — оба допустимы по разделу 16 ТЗ).
- Раздел 13 ТЗ: если решите остаться на GigaChat в production — это уже
  соответствует Варианту B; если понадобится Anthropic/другой зарубежный
  AI API — требует отдельного согласования (раздел 13.3 ТЗ), сейчас это
  оставлено только как опция для локальной разработки.
