# AGRAVIA — ИИ-чат-бот «Алиса» для сайта

Реализация по ТЗ «AI-бот AGRAVIA 2027» (раздел 24, приоритет P0):
автоматическая сегментация без обязательного выбора роли, семантический
поиск с confidence-уровнями (HIGH/MEDIUM/LOW), уточняющие вопросы,
учёт контекста диалога, RAG-guardrails против отсебятины и джейлбрейков,
передача заявки менеджеру только по запросу пользователя, отделённая
от AI-контура.

LLM-провайдер по умолчанию — **Groq** (бесплатный, быстрый, не требует
сертификата НУЦ Минцифры — удобен для разработки/демо). ⚠️ **Это
зарубежный AI API.** Раздел 13.3 ТЗ прямо запрещает отправку
пользовательских сообщений в Groq/OpenAI/Anthropic/Gemini без
отдельного согласования — Groq стоит дефолтом только ради простоты
локального старта. Перед production переключите `LLM_PROVIDER` на
`gigachat` (согласованный Вариант B, раздел 13.2 ТЗ, бесплатный лимит
1 000 000 токенов/мес на физлицо) либо на локальную LLM (Вариант A,
раздел 13.1 ТЗ). Anthropic (Claude) также оставлен как опциональная
платная альтернатива для разработки — под тем же ограничением раздела
13.3. Семантический поиск (embeddings) при этом всегда идёт через
GigaChat, если задан `GIGACHAT_AUTH_KEY`, — независимо от того, какой
`LLM_PROVIDER` формирует сам ответ.

## Структура проекта

```
agravia-bot/
├── backend/
│   ├── main.py            # FastAPI: /api/chat, /api/handoff, /api/health + подключает alice.py
│   ├── alice.py            # (опционально) вебхук навыка Яндекс.Алисы — см. раздел внизу
│   ├── chat_engine.py      # Логика диалога: тема+роль -> (одно уточнение) -> факты -> короткий ответ;
│   │                       # общая для /api/chat и alice.py
│   ├── router.py           # LLM-классификатор темы (intent) и роли пользователя с учётом состояния диалога
│   ├── kb_store.py         # Загрузка kb.json, выборка элементов по темам (поле topics)
│   ├── retrieval.py        # Ранжирование фактов внутри темы (embeddings либо fuzzy+стемминг)
│   ├── llm.py              # Вызов LLM (Groq/GigaChat/Anthropic), промпт ответа, embeddings, повтор при 429
│   ├── text_format.py      # Очистка Markdown из ответов (виджет показывает чистый текст)
│   ├── qa/run_qa.py        # QA-набор из ТЗ v2 (88 кейсов, включая цепочки) — прогон против живого бота
│   ├── analytics.py         # Логи: analytics.jsonl (раздел 18 ТЗ) и unanswered.jsonl (раздел 19 ТЗ)
│   ├── handoff.py           # Передача заявки менеджеру (Telegram + лог-файл), отделена от AI-контура
│   ├── kb.json               # База знаний: common (6) + visitor (27) + exhibitor (105), с intent/examples
│   ├── kb_embeddings_cache.json  # Кэш embedding-векторов базы (создаётся автоматически, не коммитить)
│   ├── requirements.txt
│   └── .env.example
└── widget/
    ├── widget.js         # Встраиваемый чат-виджет для сайта (ванильный JS, без сборки)
    └── demo.html          # Тестовая страница для widget.js
```

## Как это работает

ТЗ v2: `запрос → тема и роль → (одно уточнение, если без него нельзя) → факты
базы по теме и роли → короткий ответ → только если по теме данных нет —
менеджер`. Вся логика — в `chat_engine.handle_message()`.

1. **Тема и роль определяет LLM-роутер** (`router.py`), а не совпадение слов:
   разговорные и перефразированные формулировки одного вопроса ("где взять
   бейдж", "куда нажать, чтобы прийти") приводят к одной теме. Роутеру даны
   *описания* тем и ролей (посетитель, экспонент, потенциальный участник,
   застройщик) — ни одна конкретная фраза в код не зашита.
2. **Состояние диалога явное** (`state`: роль, прошлая тема, ожидаемое
   уточнение). Сервер ничего не хранит: виджет присылает `state` обратно
   каждым запросом (Алиса держит его в сессии). Поэтому роль сохраняется,
   короткие вопросы ("а демонтаж?", "а сколько стоит?") продолжают тему,
   ответ на уточнение ("я экспонент") закрывает его, а исправление
   ("нет, я про билет") заменяет прежнюю тему и роль.
3. **Одно уточнение.** Если ответ зависит от роли, а она неизвестна
   (пропуск, бейдж, заезд, транспорт), бот задаёт один короткий вопрос и не
   повторяет его. Даты, место, программа и т.п. роль не спрашивают.
4. **Факты по теме.** В `kb.json` у элементов есть поле `topics`
   (связь "тема → какие факты за неё отвечают", не зависит от формулировки).
   Внутри отобранного набора факты ранжируются под вопрос
   (`retrieval.rank`), для произвольных вопросов (`other`) — поиск по всей
   базе в сегментах роли.
5. **Ответ** строится моделью только по этим фактам (промпт запрещает
   выдумывать даты, цены, ссылки, регламенты), коротко и без Markdown;
   `text_format.clean_markdown` дополнительно вычищает служебные символы.
6. **Менеджер — последний шаг.** "Данных нет" говорится прямо и только после
   классификации и попытки ответа по базе; на вопросах вне темы, приветствии,
   "помоги" и бессмысленном вводе бот к менеджеру не отправляет. Контакты и
   заявка на участие предлагают форму `/api/handoff` (раздел 14 ТЗ v1: форма
   отделена от AI-контура), которая пишет в `logs/handoffs.jsonl` и в
   Telegram (`TELEGRAM_BOT_TOKEN` / `TELEGRAM_MANAGER_CHAT_ID`).

Каждый ход бота = 2 вызова LLM (роутер + ответ), см. ограничение по токенам
Groq в разделе про настройку LLM ниже.

## Настройка LLM

### Groq (по умолчанию, для разработки)

Самый быстрый способ запустить бэкенд локально:

1. Зарегистрируйтесь на https://console.groq.com и создайте ключ на
   странице https://console.groq.com/keys.
2. Вставьте его в `.env` как `GROQ_API_KEY`. Сертификаты не нужны.
3. `LLM_PROVIDER=groq` уже стоит по умолчанию — ничего больше менять
   не нужно.

⚠️ **Лимиты.** На бесплатном тарифе Groq (`on_demand`) — 8 000 токенов в
минуту на модель. Один ход бота (роутер + ответ) тратит 3–4 тыс. токенов, то
есть ~2 хода в минуту: при превышении Groq отвечает `429`, бэкенд ждёт указанное
в ошибке время (до `RATE_LIMIT_MAX_WAIT` секунд) и повторяет, но под реальной
нагрузкой этого мало. Для работы с посетителями нужен платный Dev Tier Groq
либо согласованный провайдер (GigaChat).

⚠️ Помните про раздел 13.3 ТЗ (см. предупреждение в начале README) —
Groq годится для разработки и демо, но не для production без отдельного
согласования. Обратите внимание: у Groq нет embeddings API, поэтому
семантический поиск (раздел 6 ТЗ) при `LLM_PROVIDER=groq` будет
работать только если ДОПОЛНИТЕЛЬНО настроен `GIGACHAT_AUTH_KEY` (см.
ниже) — без него бэкенд откатится на менее точный fuzzy-поиск
(`backend/retrieval.py`), но не упадёт.

### GigaChat (согласованный вариант для production)

1. Зарегистрируйтесь на https://developers.sber.ru обычным аккаунтом.
2. В личном кабинете откройте раздел **GigaChat API** → «Создать
   проект» → тариф **GigaChat API PERS** (для физлиц, тот самый
   бесплатный 1 млн токенов/мес).
3. На вкладке проекта нажмите «Получить доступ» — там будет готовый
   **Authorization key** (это уже Base64 от `client_id:client_secret`,
   копировать/кодировать самому не нужно). Вставьте его в `.env` как
   `GIGACHAT_AUTH_KEY`.
4. Установите сертификат НУЦ Минцифры — без него будет ошибка
   `CERTIFICATE_VERIFY_FAILED`, потому что GigaChat использует
   российский корневой сертификат, которого нет в обычных системных
   хранилищах. Самый быстрый способ (добавляет сертификат в бандл
   `certifi`, которым пользуется Python):

   ```bash
   curl -k "https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt" -w "\n" >> $(python3 -m certifi)
   ```

   Выполните это в том же окружении (venv/Docker-образе), где будет
   работать бэкенд.
5. Установите `LLM_PROVIDER=gigachat` в `.env` (для production —
   обязательно; для разработки можно оставить `GIGACHAT_AUTH_KEY`
   заданным даже при `LLM_PROVIDER=groq` — тогда GigaChat будет
   использоваться только для embeddings/поиска, а Groq — для ответов).

Если на каком-то этапе шаг 4 неудобен (например, временно тестируете
локально) — можно на время поставить `GIGACHAT_VERIFY_SSL=false` в
`.env`, но это отключает проверку SSL-сертификата и **не должно**
использоваться в продакшене.

### Если понадобится Anthropic вместо Groq/GigaChat

```
LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
```

Anthropic — платный (пробного бесплатного лимита, сравнимого с
GigaChat PERS, у него нет), но не имеет региональных ограничений
доступа, если сервер бэкенда физически не в России.

## Запуск локально

```bash
cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # впишите GROQ_API_KEY (см. выше); GIGACHAT_AUTH_KEY — опционально, для семантического поиска

export $(cat .env | xargs)   # или используйте python-dotenv/systemd env
uvicorn main:app --reload --port 8811
```

Откройте `widget/demo.html` через любой статический сервер
(например `python3 -m http.server 8000` из папки `widget/`) — виджет
достучится до `/api/...` по адресу, указанному в `data-api`.

## Встраивание на сайт (Фаза 5.3 роадмапа)

Одна строка в футер сайта:

```html
<script src="https://ВАШ_ДОМЕН/widget/widget.js"
        data-api="https://ВАШ_ДОМЕН/api"></script>
```

Бэкенд по умолчанию сам отдаёт файлы виджета по пути `/widget/...`
(смонтировано в `main.py`), так что для старта достаточно поднять
только бэкенд.

## Деплой в продакшен

- ⚠️ **Сначала переключите `LLM_PROVIDER` с `groq` на `gigachat`**
  (или локальную LLM) — Groq по умолчанию стоит только ради удобства
  разработки и не соответствует разделу 13.3 ТЗ без отдельного
  согласования (см. предупреждение в начале README).
- Задеплойте `backend/` как обычное FastAPI-приложение (uvicorn/gunicorn
  за nginx, либо Docker; сама база `kb.json` — часть образа/репозитория).
  Сервер может быть в России — GigaChat туда и рассчитан.
- Обязательно сузьте `allow_origins` в `main.py` до домена вашего сайта
  вместо `"*"`.
- Не забудьте про сертификат НУЦ Минцифры на сервере (шаг 4 выше) —
  в Docker-образе его нужно ставить на этапе сборки образа.
- Переменные окружения — `GIGACHAT_AUTH_KEY` обязателен при
  `LLM_PROVIDER=gigachat` (нужен и для embeddings/семантического поиска
  независимо от LLM_PROVIDER — см. раздел про настройку LLM выше),
  `TELEGRAM_BOT_TOKEN` / `TELEGRAM_MANAGER_CHAT_ID` опциональны (без них
  заявки всё равно сохраняются в `logs/handoffs.jsonl`).
- Логи диалогов (`logs/dialogs.jsonl`) и заявок — то, что нужно будет
  регулярно разбирать на Фазе 8 роадмапа (какие вопросы не покрыты
  базой, где бот ошибался).

### Деплой на Vercel

В репозитории уже есть `vercel.json` + `api/index.py` (реэкспортирует
FastAPI `app` из `backend/main.py`) и корневой `requirements.txt` — просто
подключите репозиторий в Vercel, framework preset можно оставить "Other".

1. **Project → Settings → Environment Variables** — добавьте как минимум
   `LLM_PROVIDER` и `GROQ_API_KEY` (или `GIGACHAT_AUTH_KEY` +
   `LLM_PROVIDER=gigachat` для production, см. выше); опционально
   `TELEGRAM_BOT_TOKEN`/`TELEGRAM_MANAGER_CHAT_ID`.
2. **Deployments → ⋯ → Redeploy** — переменные окружения применяются
   только к новым деплоям.
3. Виджет отдаётся тем же бэкендом по `/widget/widget.js` — на сайте
   укажите `data-api="https://ВАШ-ПРОЕКТ.vercel.app/api"`.

Важные ограничения serverless-окружения (учтено в коде, но держите в
уме): файловая система деплоя read-only везде, кроме `/tmp` —
`backend/log_paths.py` автоматически откатывает логи и кэш embedding-
векторов (`kb_embeddings_cache.json`) туда, если `backend/logs` не
доступен для записи. Но `/tmp` не персистентен между вызовами функции,
поэтому: (а) `logs/*.jsonl` там ничего не накопят — для реальной
аналитики (раздел 18-19 ТЗ) в этом сценарии нужна внешняя БД, а не
файлы; (б) кэш embeddings может пересчитываться на каждом холодном
старте, расходуя лимит токенов GigaChat. In-memory `SESSIONS` в
`alice.py` (навык Алисы) по той же причине ненадёжен на serverless —
для сайта это не влияет, `/api/chat` и так не хранит состояние на
сервере (историю диалога передаёт сам виджет).

## Обновление базы знаний

`kb.json` теперь состоит из трёх сегментов (раздел 4 ТЗ): `common`
(6 общих интентов — даты, часы работы, место, организатор, про AGRAVIA
и iAGRI), `visitor` (27) и `exhibitor` (105). Каждый элемент — это
интент (раздел 7 ТЗ): `category`, `question`, `answer`, плюс `intent`
(уникальный id для аналитики/лога unanswered) и опциональный список
`examples` — альтернативных формулировок того же вопроса и `topics` — к каким
темам роутера (`dates`, `location`, `visitor_reg`, `participation`,
`pass_exhibitor`, `pass_builder`, `entry`, `montage`, `demontage`,
`equipment_in`, `equipment_out`, `vehicle`, `visitor_car`, `program`, `cabinet`,
`contact`, `general`) относится факт. Новый факт без `topics` всё равно
находится вопросами "по любой другой теме" (`other`), но на размеченные темы
(например "когда монтаж") попадает только с нужным тегом. Формат:

```json
{
  "common": [
    {
      "intent": "common.event_dates",
      "category": "Даты и время",
      "question": "Когда пройдёт выставка AGRAVIA 2027?",
      "examples": ["Когда выставка?", "Даты AGRAVIA", "Какого числа AGRAVIA?"],
      "topics": ["dates"],
      "answer": "..."
    }
  ],
  "visitor": [ {"intent": "visitor.bilet_i_registraciya.01", "category": "...", "question": "...", "examples": [], "answer": "..."} ],
  "exhibitor": [ ... ]
}
```

Чтобы добавить или изменить вопрос — редактируйте `kb.json` напрямую
(обычный JSON), при желании добавьте `examples` с 2-4 перефразировками,
и перезапустите бэкенд. Если используется semantic search (настроен
`GIGACHAT_AUTH_KEY`), новые/изменённые тексты автоматически
переembeddятся при следующем старте (кэш в `kb_embeddings_cache.json`
ключуется по хэшу текста, старые записи не трогаются — так экономится
лимит токенов).

## Тестирование

QA-набор из ТЗ v2 (88 кейсов, включая цепочки "Я экспонент → Когда заезд?")
лежит в `backend/qa/run_qa.py` и прогоняется против работающего бота по HTTP
ровно так, как это делает виджет (с историей и `state`). В кейсах нет ответов
бота и подгонки под фразы — только входные реплики и проверяемые свойства
(ожидаемая тема, "уточнить/ответить", факты, которых не должно быть выдумано).

```bash
cd backend
python qa/run_qa.py --pause 14          # --pause нужен на бесплатном Groq (лимит токенов/мин)
python qa/run_qa.py --only 33-40,72-81  # перепрогнать часть набора
```

Результаты — `backend/qa/results.json`; итоговую оценку OK / Частично /
Ошибка ставит человек по ответам (критерии — раздел 8 ТЗ v2). Параметр
`"debug": true` в запросе к `/api/chat` возвращает в ответе ошибки провайдера
(например `429`) — удобно для диагностики.

Ручные проверки, которые стоит делать при изменениях логики:

- **Перефразировки:** разные формулировки одного вопроса — одна тема и
  эквивалентный ответ.
- **Роль и контекст:** "Мне нужен пропуск" → "Я экспонент"; "Мне нужен пропуск"
  → "Нет, я про билет"; "Когда монтаж?" → "А демонтаж?".
- **Одно уточнение:** второе подряд уточнение по той же теме не задаётся.
- **Вне темы:** анекдот/погода/спорт — возврат к теме AGRAVIA, без менеджера;
  "asdfgh" — просьба переформулировать.
- **Формат:** в ответах нет `**`, `##`, `` ` ``; ответ умещается в окно виджета.
- **Хендофф:** "Да, соединить с менеджером" → заявка в `logs/handoffs.jsonl`
  (и в Telegram, если настроено).

## Опционально: навык Яндекс.Алисы

В проекте также есть `backend/alice.py` — реализация вебхука для
настоящего голосового/текстового навыка Алисы (Yandex Dialogs), на
случай если он вам тоже понадобится позже. Это отдельная,
необязательная вещь: навык Алисы работает только через приложение
Яндекса/колонки/Яндекс Браузер, а не как чат-окно на сайте — сайт
обслуживает `widget/widget.js`. Оба используют одну и ту же базу
знаний и логику guardrails, включать `alice.py` не обязательно —
если он не нужен, можно просто не регистрировать навык в консоли
Яндекса, на работу сайта это никак не влияет.

## Соответствие ТЗ и что ещё осталось

**ТЗ v2 (логика диалога, QA-приёмка):** реализовано — определение темы и роли
(в т.ч. потенциальный экспонент и застройщик), сохранение роли в диалоге,
исправление темы ("нет, я про билет"), одно уточнение вместо угадывания,
менеджер как последний шаг, ответы без Markdown и короткие, off-topic /
приветствие / "помоги" / мусорный ввод без отправки к менеджеру. Результаты
собственного прогона QA-набора и список вопросов, на которые бот не уверен или
где данных нет в базе, — в отчёте, переданном вместе с этой версией.
